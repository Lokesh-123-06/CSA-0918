# Assignment 2 – CO2 Report

## Q1 – Building Text Under Load: String, StringBuilder or StringBuffer (6)
String is immutable; repeated concatenation in a loop repeatedly creates intermediate strings and copies accumulated characters. For n equal-sized fields, copied characters can grow quadratically, O(n²). StringBuilder uses a mutable character buffer and appends in amortised O(1) per append, O(total output length) overall; StringBuffer provides synchronized methods and additional contention cost. Use StringBuilder for one ticket built by one thread; use a synchronized logger or a dedicated single-writer logging service for a shared multi-threaded log. StringBuffer is a possible simple shared mutable buffer but synchronizing the complete logical record is also necessary.

Three workloads: (1) one short 6-field ticket, (2) 10,000 tickets × 50 fields, (3) 100,000 tickets × 20 fields. Benchmark warm-up plus repeated runs with System.nanoTime; report median/mean and heap delta as approximate only. Intermediate-object count is an estimate because JVM optimisations vary. StringJoiner is convenient for delimiter-separated fields; String.format is readable but formatting overhead is usually higher; String.join is suitable when fields are already collected. See Q1 source.

## Q2 – ArrayList, LinkedList and ArrayDeque (4)
ArrayList: append amortised O(1), indexed access O(1), front/middle insertion and removal O(n) due to shifting, iteration O(n). LinkedList: end operations O(1), indexed access O(n), middle insertion O(1) only after locating node (overall O(n)), iteration O(n); each element requires node/link overhead. ArrayDeque: add/remove at either end amortised O(1), no indexed access, iteration O(n); it is appropriate for the changed Up Next deque but not arbitrary indexed playlist editing. A plain array has O(1) indexed reads and O(n) shifts for insert/remove. Use Q2 benchmark for three sizes and operation-specific timing.

## Q3 – hashCode–equals contract (6)
HashSet uses hashCode to choose a bucket and equals to distinguish collisions within it. Equal objects must have equal hash codes. If equals compares regNo but hashCode remains identity-based, duplicate registrations can land in different buckets and both be stored. Correct Student is immutable and hashes regNo. Mutating a hash key after insertion can make it unreachable in its original bucket; remove and reinsert after changing identity, or make identity fields final. TreeSet offers O(log n) operations if comparator is consistent with equality; HashMap keyed by regNo offers average O(1) lookup and stores one value per key.

## Q4 – Pharmacy inventory maps (6)
HashMap gives average O(1) put/get and iteration in unspecified order. TreeMap gives O(log n) put/get and naturally sorted keys. LinkedHashMap gives average O(1) put/get and insertion-order iteration. Use TreeMap for the code-ordered report and LinkedHashMap for insertion-order report; HashMap can be copied/sorted for reporting at O(n log n). Hashtable is legacy synchronized API; modern code generally uses HashMap or explicit concurrent collections. The sorted-array alternative has O(log n) lookup, O(n) insertion due to shifting and O(n) ordered traversal, with compact storage.

## Q5 – Generic ranking (7)
Leaderboard<T> accepts Comparator<? super T>, stores T, and returns a sorted copy so callers cannot mutate internal order. Comparator chain: points descending, goal difference descending, name ascending. Avoid subtraction comparators because overflow can violate transitivity; use comparingInt/reversed/thenComparing. A comparator chain is reusable for Team, Player and College. Comparable is appropriate only when a type has one natural order. Sorting costs O(n log n) time; copying uses O(n) space. Stable multi-sort needs several O(n log n) sorts and is harder to maintain.

## Q6 – Emergency triage (8)
A PriorityQueue comparator orders lower severity number first, then arrival sequence ascending. add and poll are O(log n); peek O(1); storage O(n). A plain FIFO queue ignores severity. Printing PriorityQueue directly does not guarantee sorted iteration; repeatedly poll a copy to display treatment order. A LinkedList maintained in sorted order costs O(n) insertion and O(1) removal at head. Five FIFO queues provide O(1) admission and service if the first nonempty severity is found by scanning at most five queues. Starvation can be mitigated with bounded waiting-time escalation or ageing, while preserving emergency safety policy. Benchmark three queue sizes and compare operation costs.

## Q7 – Diagnose, redesign and validate (13)
Selected limitation: repeated String concatenation while assembling many-field tickets. Bottleneck is repeated copying/allocation as output grows. Objective: preserve exact ticket text while reducing construction time and intermediate allocations. Redesign with one StringBuilder per ticket, pre-size when a reasonable estimate exists, and append fields in order. This changes construction from quadratic copied-character growth to linear growth in output length, at the cost of a mutable buffer. Compare original and revised code under the same three workloads, warm-up, repetitions and heap measurement. The short-ticket case may show negligible difference because fixed overhead dominates; large batches should favour StringBuilder. Retain plain concatenation for small fixed expressions where readability is better.

## Conclusion
Collection choice must follow access pattern and correctness requirements. Use StringBuilder for incremental text, ArrayList for indexed playlists, ArrayDeque for two-ended queues, HashSet with correct equality for de-duplication, suitable Map variants for ordering, Comparator for reusable ranking and PriorityQueue for severity scheduling. The source programs provide repeatable experiments; timings must be recorded on the student's own machine.
